# KIKO 桌宠 2D 骨骼动画重建实施方案（交给本地千问执行）

> 目标：以仓库原版 `kiko.png` 为唯一角色外观母版，完成真正可运行的 2D 骨骼动画桌宠。本文是实施规格与验收标准，不是已完成声明。请本地千问按阶段逐项执行，先检查仓库再改代码，禁止凭空编造素材或用整张图片的 CSS 变换冒充骨骼动画。

## 0. 最高优先级约束

1. **角色一致性**：必须保留原版 KIKO 的白色圆润熊猫头、黑耳朵/眼圈、眼睛、粉色脸颊、蓝色带 K 字连帽卫衣、黑色手脚、原有 3D 毛绒质感、比例和配色。以 `kiko.png` 为视觉标准。
2. **不允许替换角色**：不准使用其他熊猫图片、图库素材、AI 重新设计的陌生熊猫替代 KIKO。AI 仅可辅助补绘原图中被遮挡后必需的区域，且必须以原图为参考并逐项人工比对。
3. **不允许假动画**：不准通过旋转/缩放/平移整张 `kiko.png`、CSS keyframes 或逐帧换几张姿势图来声称实现骨骼动画。可以保留少量 UI 微动效，但角色肢体必须由骨骼/网格变形驱动。
4. **真实分层**：头、躯干、左右手臂、左右腿等需要独立可控；关节处必须有合理遮挡、补绘和连接，不能露白洞、断层或明显拼贴边。
5. **保留原有桌宠能力**：透明置顶窗口、拖动、吸边、位置记忆、单击/双击、右键菜单、AI 事件联动等已有功能不得因动画重构而退化。
6. 不要在未完成资源、接入和验收前宣称完成。遇到素材缺失要明确记录，不要用虚构数据填充。

## 1. 先审计项目（禁止直接大改）

- 检查 `package.json`、`src/pet.html`、`src/pet-preload.js`、`src/main.js`、`src/public/kiko/`、`kiko.png` 和现有动画内核 `src/pet/animation/`。
- 识别当前 Electron/Vite 入口、窗口尺寸、图片加载路径、IPC 事件、桌宠状态来源和打包方式。
- 运行现有 lint/build/test，记录基线结果；若没有测试脚本，补充可运行的测试，不得伪报通过。
- 在改动前建立清单：哪些旧交互必须保持、哪些文件会被改、资源文件尺寸/格式/透明通道。
- 重点检查现有 `Bone.js`、`Skeleton.js`、`Skinning.js`、`MotionMixer.js`、`AnimationEngine.js`，不要盲目沿用有缺陷的代码。当前内核只是初始框架，不代表已完成生产级动画。

## 2. 角色图像拆分与重建（最关键）

### 2.1 先分析母版
- 读取仓库根目录 `kiko.png` 的真实像素，记录宽高、RGBA/透明通道、非透明边界、背景和角色整体边界。
- 输出 `docs/kiko-asset-analysis.md`，记录原图特征、坐标系、每个部件的边界框和拆分难点。
- 保存不可修改的原图副本或校验哈希；禁止覆盖原始 `kiko.png`。

### 2.2 需要的独立部件
至少拆分并输出透明 PNG（部件坐标统一到原图画布或记录精确锚点）：
- `head.png`：头部主体（包含原图头部毛绒轮廓）；耳朵若需独立摆动则另拆 `ear_l.png`、`ear_r.png`。
- `face/eyes_open.png`、`face/eyes_closed.png`、必要时 `face/mouth_*.png`；五官必须保持原样，不可改变眼圈、眼睛、腮红造型。
- `torso.png`：蓝色 K 字卫衣躯干，K 字图案和衣服纹理必须完整。
- `arm_upper_l.png`、`arm_lower_l.png`、`hand_l.png`；右侧对应部件。
- `leg_upper_l.png`、`leg_lower_l.png`、`foot_l.png`；右侧对应部件。
- 如原图姿势导致某部位不可见，按真实解剖连接和衣物连续性补绘被遮挡区域；补绘必须参考原图颜色、光照、材质和透视，且不得擅自新增装饰。
- 所有部件应有重叠余量（关节覆盖区），避免旋转时露缝。为部件记录 pivot（关节轴）和 z-order。

### 2.3 素材制作策略
- 优先用图像分割/手工路径提取原图轮廓，再用修复/绘制补齐遮挡部分；自动分割结果必须逐张检查。
- 如果本地千问具备视觉能力，可让它对原图做部件定位和边界建议；不能只靠文字模型猜像素坐标。
- 允许使用图像编辑模型辅助补绘，但提示词必须要求“严格沿用上传的 KIKO 原图角色设计，只补全指定被遮挡区域，不改头身比例、服装、五官、配色和材质”。输出后做叠图对比。
- 不允许将原图简单矩形裁切后直接当成完整肢体。矩形裁切可以作为初始选区，不是最终资产。
- 每个部件输出透明 PNG，并生成 `assets/rig/parts/manifest.json`，包含原图尺寸、部件文件、源图坐标、pivot、zIndex、锚点和补绘说明。
- 同时生成一张部件拼装预览图和一张分层检查图，便于肉眼检查是否仍与原版一致。

## 3. 骨架定义与网格蒙皮

### 3.1 骨骼层级
建议骨骼命名（可按原图结构微调，但要左右对称、命名统一）：
```text
root
├─ body
│  ├─ head
│  │  ├─ ear_l
│  │  ├─ ear_r
│  │  └─ face
│  ├─ shoulder_l -> upper_arm_l -> forearm_l -> hand_l
│  ├─ shoulder_r -> upper_arm_r -> forearm_r -> hand_r
│  ├─ hip_l -> thigh_l -> shin_l -> foot_l
│  └─ hip_r -> thigh_r -> shin_r -> foot_r
```
- 每根骨骼包含 name、parent、bind position、rotation、length、scale、pivot。
- 关节位置必须按原图实际像素测量，不能凭感觉填数。
- 建立 bind pose 和 inverse bind matrix；骨骼局部矩阵、世界矩阵、父子层级更新顺序必须正确。

### 3.2 网格与权重
- 为各独立部件生成三角网格，保留原图纹理；网格边缘贴合部件轮廓，关键关节附近增加顶点密度。
- 顶点权重总和必须为 1；通常每顶点最多 4 根骨骼影响。权重平滑但不能让卫衣图案或脸部跨关节扭曲。
- 头脸、卫衣 K 字、手脚等刚性区域优先使用刚性或高权重绑定；肩、肘、髋、膝等区域用平滑权重。
- 明确处理三角形 UV/源纹理映射、透明边缘抗锯齿、重叠绘制和 z-order。
- 输出 `assets/rig/rig.json`（骨架、mesh、权重、部件引用、bind pose）并通过 schema 校验。
- 若当前 CPU 逐三角形绘制性能不足，评估 PixiJS/WebGL 或 Canvas 方案；优先保证 Electron 兼容和可维护性，不能未经测量就引入重型依赖。

## 4. 动画运行时要求

### 4.1 必须具备
- 骨骼局部/世界矩阵和 inverse bind pose。
- 网格线性混合蒙皮（或更合适的 2D deform 实现）。
- 动画片段采样、关键帧插值（至少线性，旋转角要处理跨 360°）、动作循环。
- 动作层权重、淡入淡出、优先级/遮罩、打断规则。
- 状态机、时间步长上限、暂停/恢复、窗口失焦处理。
- 低频状态事件不能导致动作重入或叠加失控。
- 渲染使用透明画布，支持 devicePixelRatio，清理 RAF，窗口关闭时释放资源。
- 动画采样与渲染分离，避免把 AI 网络请求放入动画帧循环。

### 4.2 动作清单
所有动作都必须由对应骨骼和网格驱动，需制作预览视频或 GIF，并在桌宠窗口实机检查：
1. **idle 自然待机**：轻微呼吸（胸腔/躯干）、头部微摆、自然眨眼、耳朵细微弹性；动作幅度小，不要像机械摇摆。
2. **thinking 思考**：头部轻微倾斜、眼神/眨眼状态变化、手部靠近下巴或身体（若原始部件结构允许）；节奏舒缓。
3. **working 工作中**：轻微专注姿态、手臂/头部细微动作；不能大幅乱动干扰办公。
4. **success 成功**：短促开心跳跃、双臂抬起/挥动、落地缓冲和二次回弹。
5. **error 失败/受阻**：短暂低头/肩部下沉，再回到待机；不要过度夸张。
6. **jump 跳跃**：下蹲蓄力、起跳、空中姿态、落地压缩、弹性恢复，脚与身体协调。
7. **belly_pat 拍肚皮**：一只手臂抬起，前臂/手掌触碰卫衣腹部，躯干轻微响应；手掌必须与躯干有正确遮挡。
8. **roll 打滚**：身体重心移动、四肢收拢、身体旋转并恢复站姿；如果当前二维素材不能可信实现完整滚动，先实现侧倾翻身版本并明确标注，不准整张图旋转伪装。
9. **stretch 伸懒腰**：双臂上举、躯干拉伸、头部轻仰、回落缓冲。
10. **drag/被拖动**：拖动时根据鼠标速度和方向产生轻微惯性倾斜，松开后弹性恢复；不影响 Electron 窗口拖动逻辑。
11. **sleeping 睡觉**：闭眼、呼吸、轻微头部下垂；若睡眠状态已有独立素材，需检查是否为原版 KIKO 并统一资产规范。

### 4.3 动作片段格式
采用可读 JSON/JS clip 格式，包含 duration、loop、tracks/keyframes、easing、事件标记。动作数值以骨骼 bind pose 为基准，clip 存储偏移量，不要每帧覆盖丢失基姿态。提供一个可运行的示例片段和动作预览页。

## 5. 状态机与桌宠交互接入

- 先梳理现有桌宠 IPC 和业务状态，不要改动或删除既有事件名。
- 建立明确状态：idle、thinking、working、success、error、sleeping、dragging、interacting。
- 定义状态优先级与过渡：dragging/interacting 可短暂覆盖 idle；thinking/working 随 AI 生命周期切换；success/error 是短暂反馈，结束后回到上一个有效状态或 idle。
- 连续事件要防抖；同一状态不重复重启动作；高优先级动作结束后恢复正确状态。
- 把动画控制封装为 PetAnimator API，例如 `setState(state, payload)`、`playAction(name, options)`、`stopAction(name)`，由 pet 页面调用。
- 在 `src/pet.html` 接入动画 canvas/renderer，保持透明窗口、点击穿透策略、层级、尺寸和缩放正确。
- 保留旧 CSS 仅用于气泡、阴影或 UI，不得再控制角色主体骨骼。
- 确保位置拖动、吸边、鼠标点击、双击速记、右键菜单与动画事件互不冲突。

## 6. 调试工具与资产验收

新增一个开发专用 Rig Preview 页面/模式：
- 显示原图、部件图层、骨架线、pivot、网格三角形、权重热图。
- 可选中骨骼并拖动/旋转，观察局部和世界变换。
- 可切换动作、暂停、逐帧、调整播放速度。
- 可显示 FPS、绘制耗时、网格顶点数、透明边缘和异常权重。
- 能一键导出当前 rig JSON 和预览截图。

视觉验收逐项打勾：
- [ ] 头、五官、腮红和 K 字卫衣与原图一致，无变形失真。
- [ ] 手臂、腿在关节弯曲时无露洞、断裂、明显拉伸。
- [ ] 前后遮挡关系正确，手掌拍肚皮时不会穿透躯干。
- [ ] 透明边缘无黑边、白边、锯齿光晕。
- [ ] 所有动作自然、有缓入缓出，不抖动、不抽帧、不漂移。
- [ ] 待机长时间运行无 RAF 泄漏、内存持续增长或 CPU 异常。
- [ ] 桌宠原有拖动、吸边、记忆位置、点击、双击、右键和 AI 联动均正常。
- [ ] Windows 实机不同 DPI/缩放下尺寸和点击区域正确。

## 7. 测试与交付标准

### 自动化测试
- 骨架父子层级、矩阵、bind pose/inverse bind、reset。
- 网格权重归一化、非法骨骼引用、越界索引、退化三角形。
- 动作关键帧插值、循环、淡入淡出、优先级、打断与恢复。
- 状态机连续事件、防抖和动作完成回归。
- renderer resize/DPR、start/stop、资源释放。
- Electron 桌宠原有交互回归测试。

### 性能目标
- 桌宠常态目标 60 FPS；低配设备允许稳定 30 FPS。
- 单帧动画逻辑和渲染尽量控制在 8ms 内（以实际测量为准）。
- 不能因为 2D 动画让主进程承担持续高 CPU 计算。
- 若 CPU 蒙皮不达标，再评估 WebGL/GPU 路线，先给出基准测试数据。

### 最终交付文件
- `assets/rig/parts/*.png`：全部透明部件。
- `assets/rig/rig.json`：骨架、网格、权重、锚点、z-order。
- `assets/rig/manifest.json`：资产来源和坐标说明。
- `src/pet/animation/`：稳定的运行时和状态机。
- `src/pet/animations/`：各动作片段。
- `src/pet.html`：正式接入桌宠。
- `tools/rig-preview/` 或等价调试工具。
- `docs/kiko-asset-analysis.md`、`docs/kiko-animation-acceptance.md`。
- 测试报告、build 结果、Windows 实机截图/录屏。

## 8. 建议执行顺序（严格按阶段，不要跳过）

- **阶段 A：项目审计**。确认项目结构、原图规格、当前代码缺陷，形成审计文档。
- **阶段 B：角色拆分**。先完成原图部件分层、遮挡补绘、拼装预览；用户确认角色外观一致后才继续。
- **阶段 C：骨架和网格**。完成骨骼定义、pivot、网格和权重，先用调试器验证弯曲。
- **阶段 D：动画内核**。修复/完善矩阵、蒙皮、动作混合、状态机和测试。
- **阶段 E：制作动作**。先 idle/thinking/working，再 jump/success/error/stretch/belly_pat/roll。
- **阶段 F：Electron 接入**。保留旧功能，逐项回归。
- **阶段 G：性能与视觉验收**。Windows 实机运行，录屏并完成验收表。
- **阶段 H：整理提交**。更新 README、变更日志和 PR，提供未完成项清单。

每个阶段完成后再进入下一阶段；若阶段 B 的素材质量不合格，停止后续动画制作，不要用假动作掩盖。
